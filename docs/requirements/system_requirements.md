## 1. システム化の範囲（with）

| 要求ID | 今回システムで実現するか | 理由 |
| --- | --- | --- |
| BR-01 | 実現する | タグ（5種類）で相手に合う商品に絞り、類似度の高い順に返す（FR-03・04、6.2）。Exhibit 5の「入力→候補取得→順位付け→結果」の中心になる |
| BR-02 | 実現する（BR-01に統合） | 一致したタグ名を商品カードに表示する。理由の文章は作らない。あわせて説明文の冒頭2行を表示する（FR-05、6.3） |
| BR-03 | 実現する（形を変える） | 予算+20%の追加提案は見送り、代わりに予算の下限・上限を500円単位で利用者が自分で選べるようにする（FR-08、11/14 チームMTG）。既存の検索APIは下限・上限に対応しているので、画面の変更だけで作れる |
| BR-04 | 測り方のみ | モックはローカルで動かすだけで、購入率は測れない（Exhibit 5）。本番に入れたあとに測る（要求定義書6章） |
| BR-05 | 測り方のみ | 単価の変化も本番に入れたあとに測る。予算の下限・上限の選択（FR-08）を入れた前後で比べる |
| BR-06 | 実現しない | 誕生日専用の入口は作らず、既存の検索画面を使う（11/12 チームMTG）。「誕生日ならGiftia」は長期の方向性として要求定義書に残す |
| BR-07 | 一部 | タグで見えるようになった商品で、出会えていない商品を減らす（FR-03・04）。予算の上限を自分で広げて、予算を少し超える商品も探せるようにする（FR-08） |

Exhibit 5の必須処理との対応：入力＝シーン（誕生日）・予算の下限と上限・タグ（4.2 検索画面）／候補取得＝誕生日シーン×予算の範囲×タグで商品DBから取得（6.2）／順位付け＝選んだタグとの類似度の高い順（6.2）／結果＝一致したタグ名つきの一覧（6.3）

## 2. 1〜3年後の姿と Phase1（with）

| 項目 | 内容 |

| Phase1 でやること | ・既存の検索画面で、シーンに「誕生日」を選んだときだけタグ欄を出す（予算の範囲とタグで絞る）<br>・タグは全商品に裏側で付けておき、画面でタグを選べるのは「誕生日」を選んだときだけにする<br>・全商品（約8,000件）に、5種類のタグを意味検索（ベクトル）で付ける。人が1人50件ずつ、4人で計200件を確認する<br>・選んだタグとの類似度の高い順に並べ、商品カードに一致したタグ名と説明文の冒頭2行を表示する<br>・予算の下限・上限を、それぞれ500円単位で選べるようにする（画面の変更だけ。既存の検索APIを使う）<br>これらの機能を追加したモック（ローカル用）を作成する |
| Phase1 でやらないことと理由 | ・本番公開・決済・配送：Exhibit 5で対象外<br>・LLM（文章を作るAI）：タグ付けにも画面にも使わない。タグは意味検索（ベクトル）で付ける（6.1）<br>・推薦理由の文章：作らない。タグを自分で選んで検索するので、商品カードにタグ名を出せば理由は伝わると判断<br>・送別など他のシーン：要求定義書3.2でSTEP2以降とした<br>・会員情報や送り先の利用：個人情報を扱わない（8章）<br>・予算+20%の追加提案（BR-03）：件数の表示や別画面への移動など作る量が多く、タグ付けの開発と重なるため見送る。代わりに予算の下限・上限を選べるようにする<br>・誕生日専用の入口：既存の検索画面で足りるため作らない<br>・商品の詳細ページ：最小限の範囲にするため作らない<br>・操作の記録：ローカルのモックでは利用データが取れないため作らない。本番ではアクセス解析ツールで取る<br>・商品自体の特徴タグ（「個性的」「万人受け」など）：今回は作らない。今回のタグは「もらう人がどんな人か」を表すものにした。<br>※今回重要と判断したのは商品自体の目線ではなく、誰にあげるか、と議論したため |
| Phase1 で検証すること（要求定義書 6章との対応） | モックで確かめるのは、タグが正しく付くかと、検索結果が妥当か（6.4のテスト）<br>①人が見て合うと思う商品に、そのタグが付いているか<br>②タグを選んだとき、合う商品が上位に来るか<br>③4人が50件ずつ（計200件）タグの付き方を見て、合っているかを確かめる（「自信を持って選べるか」の確認の代わり）<br>購入率・単価などの効果は、発表のあと本番に入れてから測る（要求定義書6章） |
| Phase2 以降 | ・Phase2：商品の詳細ページ、新商品への自動付与、誕生日以外のシーンに合わせたタグの組み合わせ、本番での効果測定（購入率・単価、BR-04・05）<br>・Phase3：家族への誕生日、送別（合意の支援）などへ広げる |

### 5.5 タグの付け方（手順）

タグは「準備 → 機械でタグを付ける（①〜③）→ 人が確かめる（④）」の順で付ける（指摘No23）。機械の計算は事前に1回だけ行って結果をDBに保存し、画面を開くたびに計算することはしない。

［11/14決定］は11/14の打ち合わせで決まったこと、［案］はまだ決まっていないこと。［案］のところはチームで確認してから進める。

※下の図の②「タグの説明」は、2026-11-18から「タグの計算用の説明文（match_text）」を指す（図は次の更新で直す）。

![タグの付け方（手順）の図](images/tag_assignment_flow.png)

画像の文字起こし（図の内容。「11/14決定」「案」「11/14未解決」は図のラベル）：

- 準備
  - A. 正解データ用の200件を先に取り分ける［200件は11/14決定、取り分け方は案］
    - 手法：8,000件からランダムに200件を選び、言い回しづくりには使わない
    - 理由：答えを見てから言い回しを作ると、正解率が実際より良く見えてしまうため
  - B. 決まり文句を取り除く［案］
    - 手法：のし・ラッピング・配送などの文を説明文から消す
    - 理由：全商品に共通する文が残ると、どの商品も同じように当たってしまうため
  - C. 言い回しの一覧をつくる［案］
    - 手法：説明文を「文の種類」にまとめ、多い順に見て「確実・弱い・除外」を決める
    - 理由：同じ文の使い回しが多く（2,000件で6,542文→873種類）、一覧なら人が読める量になるため
- 機械でタグを付ける（事前に1回だけ計算し、DBに保存）
  - ① 言い回しで分類する［案］
    - 手法：言い回しがそのまま含まれるかで「自動／要確認／なし」に分ける
    - 理由：確実なものを早く拾え、「この言葉があったから」と説明しやすい
    - 弱点：言い方が少し違うと拾えない（試作では約7割がどれにも当たらなかった）
  - （拾えなかった分を補う）
  - ② e5で意味の近さを判定する［ベクトル化・0.7程度は11/14決定、e5を使うかは案］
    - 手法：文をベクトル（意味を表す数値の並び）にし、タグの説明との類似度（0〜1）を計算。まず0.7程度以上を候補にする
    - 理由：言い方が違っても意味が近い商品を拾える
    - 弱点：なぜ近いかが見えにくい → 一番近かった文を「根拠の一文（reason）」として残す
  - ③ ①と②を合わせてタグを付ける［案］
    - 手法：①で「自動」か②で基準以上 → タグを付けて保存。①で「要確認」や②で基準に近いもの → ④で人が見る
    - 理由：①（説明しやすい）と②（取りこぼしが少ない）で、互いの弱点を補い合う
- 人が確かめる
  - ④ 正解データと比べる［4人×50件＝200件は11/14決定、比べ方・合格の割合は案］
    - 手法：Aで取り分けた200件に人が○×の正解を付け、機械の結果と比べて「合っている割合」「見逃した割合」を出す
    - 理由：正解がないと、タグ付けの良し悪しを数字で言えないため
    - 結果を見て、言い回し・タグの説明文・類似度の基準を直し、①からやり直す
- そのあと
  - 新しい商品：登録時に①〜③を流し、「要確認」だけ商品部が見る
  - それでも精度が足りないとき［11/14未解決］：口コミ（reviews）もあわせてベクトルにする


## 6. 候補の取り方と並び順（検索・絞り込み・ランキング）（with）

### 6.1 方式と選んだ理由

| 項目 | 内容 |
| --- | --- |
| 方式 | 絞り込み＋類似度による並べ替え。タグは意味検索（ベクトル）で事前に付けておき、画面を表示するたびにAIを呼ぶことはしない。LLM（文章を作るAI）は使わない |
| 選んだ理由 | ・同じ入力なら同じ順位になり、類似度という数字で「なぜこの順位か」を説明できる<br>・テストケースで良し悪しを確かめやすい<br>・画面を表示するたびにAIを呼ばないので、速度と費用が安定する<br>・要求定義書5章の案B（タグ）とそのまま対応する。予算の下限・上限は、既存の検索の条件（price_min・price_max）をそのまま使う |
| 選ばなかった方式と理由 | ・LLMでタグを付ける：LLMの「自信の度合い」は根拠を説明しにくく、同じ商品でも結果が変わることがある<br>・LLMで毎回提案を作る：出力が毎回変わり、順位の理由を説明・検証しにくい。費用と応答時間もかかる<br>・人気順（sales_count）で並べる：人気が自己強化され、Bさんにとっては「普通すぎる」になる（Exhibit 2）。既存のシーン別ランキングと変わらない（Exhibit 3）<br>・説明文のキーワード一致だけで絞る：説明文の書き方がばらばらで、表記ゆれに弱い（Exhibit 4） |

### 6.2 候補の取り方と順位の付け方

| 項目 | 内容 |
| --- | --- |
| 入力（ユーザーから受け取るもの） | ・予算の下限・上限（price_min、price_max。それぞれ500円単位で選ぶ）<br>・タグ（5種類から1〜2個。選ばなくてもよい）<br>・シーン（「誕生日」を選んだときだけタグ欄を出す） |
| 候補取得の条件 | ・product_scenes.scene_tag＝「誕生日」<br>・price_min ≦ price ≦ price_max<br>・stock＞0<br>・タグを選んだ場合：選んだタグのいずれかが product_favorite に付いている商品（タグは類似度が基準以上のときだけ付けているので、検索時に類似度の条件は足さない） |
| 順位付けのロジック | 並び順＝選んだタグとの類似度の合計が高い順<br>・タグを2つ選んだ場合、両方が付いている商品は類似度を2つ足すので、自然に上に来る<br>・同点のとき、またはタグを選ばなかったときは、評価（rating）の高い順、さらにレビュー件数（review_count）の多い順<br>・sales_count（販売数）は使わない（人気が自己強化されるのを避けるため）<br>・既存の並び替え（おすすめ／人気／評価／価格／新着）との関係は、実装しながら検討。 |
| 使うデータ（テーブル.カラム） | products：product_id、product_name、price、stock、rating、review_count、description<br>product_scenes：scene_tag<br>product_favorite：tag_id、similarity<br>tag_id（タグの定義）：tag_name、definition |

| 移行性（追加データの投入、本番のDBへの反映） | 追加データを班のDBに入れ、本番に反映できる形にしておく | 追加テーブルの作成SQLと投入スクリプトをリポジトリに置く。既存テーブルは変更しない（追加のみ） | 本番DBへの反映そのものは対象外（Exhibit 5） |
| セキュリティ | 接続情報とキーを漏らさない。個人情報を持たない | DB接続情報と、ベクトル化に外部のAPIを使う場合はそのキーを.envに置き、.gitignoreでGitHubにコミットしない。キーはタグ付けのスクリプトだけで使い、画面側に置かない。班のDBは開発環境で、本番ではない。users・ordersの個人に関わる情報は使わない |  |
| システム環境・エコロジー | 対象外 | — | 手元のパソコンとAzureの班のDBで動かすため |

## 付録A. 残課題とリスク（with）

| 内容 | 影響 | 対応（いつ・誰が） |
| --- | --- | --- |
| 自動で付けたタグが不正確（類似度が高くても意味がずれる） | 合わない商品が上位に来て、一致理由が信頼されなくなる | 4週目：200件（1人50件×4人）を人が確認し、基準の類似度（まず0.7程度）とタグの計算用の説明文を調整する（開発） |
| 説明文に手がかりが無い商品がある | タグが付かず候補から外れ、出会えない商品が残る | 4週目：付けられなかった件数を数え、扱いを商品部と決める |
| 5種類のタグの軸が混ざっている（「個性的／シンプル」はスタイル、「インテリア好き／コーヒー・お茶好き」は相手の関心） | 選ぶ側が迷う。軸の違うタグを組み合わせると、類似度の合計が偏る | 対応済み：「もらう人がどんな人か」を表す5種類にそろえた（11/14） |
| 誕生日シーンの商品には、友人向け以外（家族向けなど）も含まれる | 友人向けとして合わない商品が候補に出る | 5週目：テストケースで確認し、必要なら対象を絞る |
| 意味検索でのタグ付けがうまくいかない | タグ検索そのものが成り立たない | 4週目：早めに50件で試す。だめなら口コミ（reviews）もあわせてベクトル化することを検討する（11/14 未解決の質問）。言い回しでの分類は5.5の手順に入れた |
| タグを付ける300件の選び方が決まっていない（売れ筋上位にすると偏る） | 人気の商品にばかりタグが付き、出会えていない商品が残る | 対応済み：件数やシーンで絞らず、全商品に付ける（11/14） |
| 購入率などの効果はモックでは測れない | 発表の時点では効果を数字で示せない | 6週目：測り方の計画（要求定義書6章）を発表で示す |
