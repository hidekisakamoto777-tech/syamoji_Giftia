## 2. 画面・入力・表示の詳細

必要な場合に記入：入力制限、表示形式、状態・エラー時の扱い。

- 評価の表示（F-4、#15）：`rating` が `null` のとき、カードに「レビューなし」と表示する。`0` のときは、数字の「0」を表示する（`null` と `0` を区別する）。レビュー件数の表示も、同じ行で、矛盾しないようにする。
- `frontend/lib/api.ts` の `Gift` 型は、`rating: number | null` にする。

## 3. APIの詳細

必要な場合に記入：入出力の型・形式、検証、エラー応答。

- `GET /api/search` が返す商品の `rating`（F-4、#13）：レビューがない商品は `null`。レビューがある商品は、DBの保存値（小数1桁）を数値で返す。以前は、レビューなしを `0` で返していた（2026-11-19に変更）。
- 項目名は、`lib/api.ts` の `Gift` 型に合わせた camelCase（`reviewCount`、`matchedTags` など）。要件定義書4.3の表記（`review_count`、`matched_tags`）とは違うので、付録Bで確認する。

## 4. データ・処理の詳細

必要な場合に記入：カラムや制約、処理手順、計算式、並び順の実装方法。

- 評価（D-1、#13）：`products.rating` は、平均を小数1桁に丸めた値で保存されている（MySQLのROUNDとPythonのround()で、4.25の丸めが違う）。バックエンドで、レビューから平均を計算し直さない。DBの値を、そのまま使う。並び順（`ORDER BY p.rating DESC`）も、DBの値を使う。レビューなし（`NULL`）は、評価の高い順で最後に来る。
- DB接続（F-3、#13）：`database.py` の `fetch_all` は、`conn` を渡すと、その接続を使い、閉じない。渡さないと、今までどおり、1回ごとにつないで閉じる。`/api/search` は、`get_connection()` を1回だけ呼び、タグの検証・件数・一覧の3つの質問で使い回して、最後に `finally` で閉じる。接続のプール（複数の接続を持つ仕組み）は、Phase1では使わない。
